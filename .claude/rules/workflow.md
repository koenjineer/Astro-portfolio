# ワークフロー

## Phase 0：着手前準備（必須）

サイクル開始時、設計担当・開発担当を起動する前に PM が完了させること。

**Phase 0 完了マークが spec.md にない場合、設計担当・開発担当の起動は禁止。**

### 環境チェック
- [ ] `settings.json`（共有版）に必要ツールが全部 allow されているか確認
- [ ] Playwright が動作するか確認（`pnpm screenshot --check`）
- [ ] Figma MCP 接続確認（`mcp__figma__whoami`）

### Figma 全情報取得
- [ ] `get_variable_defs` で全カラー・タイポ取得 → spec.md「Figma変数辞書」に記載
- [ ] 親ノード（PC・SP）の `get_metadata` で全セクションのノードID取得 → spec.md「セクション構造」に記載
- [ ] 大セクション（高さ >1000px）は子ノードまで把握 → spec.md に記載
- [ ] 全セクションの Figma スクショ取得 → `handoff/screenshots/{section}/figma-{pc|sp}__{timestamp}.png` 配置

#### Figma 変数取得時の context 管理

- `get_variable_defs` 取得後、**変数数をカウント**
- **100個以下**：そのまま spec.md「Figma変数辞書」に貼り付け
- **100個超**：カテゴリ別取得（color/typography/spacing を別々の呼び出しに分割）または Top 50 のみ抽出

### 透過取得可否テスト
- [ ] 透過必要っぽいノード1つを選定（ロゴ・装飾・アイコン等）
- [ ] `get_design_context` で asset URL 取得 → curl ダウンロード
- [ ] alpha 解析で透過状態を確認
- [ ] 以下のモードを判定して spec.md「画像取得モード」に明記：

| 判定結果 | モード | 運用 |
|---|---|---|
| 4KB以下の空PNG（alpha=0 100%） | **A モード** | ユーザー手動エクスポート必須 |
| 通常サイズPNG（alpha=0 部分あり） | **B モード** | MCP で透過素材取得可能 |
| 通常サイズPNG（alpha=255 一色） | **C モード** | 写真はMCP、装飾はユーザー手動 |

### 透過必要画像リスト作成（A/C モードのみ）
- [ ] 全ノードを「透過必要 / 不要」で分類
- [ ] `.claude/handoff/user-exports/REQUEST.md` にリスト保存
- [ ] ユーザーに依頼を通知

### Phase 0 完了
全項目クリア後、spec.md に「Phase 0 完了 ✅」マークを記載。

## 1サイクルの流れ

### サイクル開始時の初期化（必須）
以下のhandoffファイルを全てクリアしてから着手：
- `.claude/handoff/spec.md`
- `.claude/handoff/review.md`
- `.claude/handoff/improvement.md`

### フロー

1. **ユーザー** → PMに FigmaURL とディレクトリ名を渡す
2. **PM** → Phase 0 を実施
3. **PM** → A/C モードなら user-exports/REQUEST.md を作成しユーザー依頼
4. **ユーザー** → 透過必要画像を手動エクスポートして配置（A/C モードのみ）
5. **PM** → cwebp 変換して `public/mock_site/{site}/images/` に配置
6. **PM** → 設計担当に指示を出す
7. **設計担当** → Q&Aをまとめてユーザーに確認
8. **ユーザー** → Q&Aに回答
9. **設計担当** → 回答を踏まえて `spec.md` 作成 → PM 報告
10. **PM** → 開発担当に実装開始指示
11. **開発担当** → セクション単位で実装（事前視覚把握 → 実装 → 完了報告）
12. **PM** → 各セクション完了後、Playwright + pixelmatch で視覚比較
13. **PM** → 差異あれば開発担当に差し戻し（修正3回まで）
14. **PM** → 差異ゼロまたは閾値以下なら、ユーザーに承認依頼
15. **ユーザー** → 承認 / 差し戻し
16. **PM** → 全セクション完了したら、ユーザーに完成報告
17. **ユーザー** → 完成確認・承認
18. **PM** → improvement.md を整理（採用/保留/棄却分類）
19. **PM** → 統合性チェック実施 → CLAUDE.md に反映
20. **PM** → 次サイクルへ

## 引き継ぎファイル（handoff）

### ファイル一覧

| ファイル | 役割 | 作成者 | 寿命 |
|---|---|---|---|
| `spec.md` | 構造仕様書 | 設計担当 | 1サイクル（毎回上書き） |
| `review.md` | 差異リスト | レビュー担当 | 1サイクル（毎回上書き） |
| `improvement.md` | 改善案リスト | PM | サイクル毎にクリア、未処理項目のみ残す |
| `escalation.md` | エスカレ報告 | PM | 発生時のみ作成 |
| `user-exports/REQUEST.md` | 透過画像依頼 | PM | A/Cモード時のみ作成 |

### improvement.md ライフサイクル

- **サイクル開始時**：improvement.md を完全クリア
- **サイクル中**：発見した改善案を即時追記（カテゴリ・優先度・ステータス付き）
- **サイクル末**：採用 → CLAUDE.md 反映 / 保留 → そのまま / 棄却 → 理由1行残して削除

### handoff ファイル更新ルール（必須・違反厳禁）

1. **更新前に必ず Read** する
2. **Write 時は全文上書き**（部分編集禁止）
3. **既存セクション見出しを改変しない**
4. **既存マークアップを維持**
5. **新規セクション追加時は末尾付近に追記**

PMは更新後に確認：セクション数の変化・表の崩れ・コードブロックの開閉が揃っているか。

### CLAUDE.md 反映時の統合性チェック

採用項目を CLAUDE.md に追加する際：
- **競合**：既存ルールと矛盾しないか
- **重複**：同じことを言っていないか
- **盲点**：新旧ルールの隙間に抜けはないか

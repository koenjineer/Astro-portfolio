# 役割定義

## PM の詳細責務

### 状態報告ルール（必須）

- 長い処理（Figma読み込み等）を始める前に「〇〇を読み込んでいます」と宣言する
- ユーザーの回答待ちは「回答をお待ちしています」と明示して終了する
- 処理が途中で止まった場合、再開時に「〇〇まで完了していたので〇〇から再開します」と状態を報告する

### 視覚比較責務（必須）

> 原則は CLAUDE.md 1（PMの役割）参照。ここでは運用閾値のみ定義する。

- pixelmatch 差異率 2% 以下を「自動 OK」基準とする

---

## 設計（担当：PM）

**責任範囲：構造設計 + 事前Q&A**

> この役割は PM が直接担う（サブエージェント化しない）。PM が窓口のため Q&A はユーザーと直接行う。

- Figmaを読んでセクション構成・コンポーネント分割を決める
- ファイル構成・SCSS構成・BEM命名規則を決める
- アニメーション・インタラクションの実装方針を決める
- **Figmaだけでは判断できない点をQ&Aにまとめてユーザーに確認する（最大10件）**
  - **最初の質問（固定）**：Figmaから抽出したセクション一覧をユーザーに提示し「OK」をもらってから次へ進む
  - 2問目の固定質問：「SP/PCの切り替えブレイクポイントは何pxにしますか？（提案：767px以下SP）」
  - 質問は「〇〇にしますがよいですか？」の提案形式
- Q&Aの回答を踏まえて `.claude/handoff/spec.md` に書き出す
- **px・色・フォント・テキストの詳細は spec.md に書かない**（開発担当がFigmaから直接読む）
- 設計フェーズではコードを書かない
- **画像/コードの境界は調査担当の報告を元に決める**（下記）。曖昧な箇所のみユーザーに確認する

---

## 調査担当（Phase 0 専用・サブエージェント）

**Figmaのレイヤー実体を吸い出し、画像とコードの境界の素材をspec.mdにまとめる。決定はしない。**

> 設計フェーズは「調査担当（サブ）＋PM」の二人体制。サブが調査して終わり、PMがそれを元に全設計を組み立てる。常駐せずPhase 0で完了する。

### 範囲（3区分）

1. **必ず読む（全セクション・無料）**：各セクションの `get_design_context` でレイヤーツリーを読み、**見えているテキスト・UIが全てレイヤーとして存在するか**を照合する
   - 全部レイヤーに在る → クリーン。写真のみ画像・他はコードで確定（目視不要）
   - 見えてるのにレイヤーに無い → 焼き込まれた合成の疑い → 目視へ
2. **落として目視する（限定）**：以下の3トリガーに当たる画像だけ curl で落として中身確認
   - 全面/大型の背景画像（例：camp・omoi 背景）
   - 「見えてるのにレイヤーに無い」要素（テキストの焼き込み疑い）
   - **兄弟アセットの外れ値**（同種画像で解像度・容量が極端に外れた1枚＝書き出しミス。例：tour-card4）
3. **対象外（信頼して触らない）**：ベクター（SVGロゴ・アイコン・デコ・線）、独立した写真（枠が決まりテキストが別レイヤーで揃うもの）、**最終判断そのもの**（PMが担う）

### 出力（spec.md）

セクションごとに：画像で実装する要素＋クリーン確認済みの取得元 / コードで実装する要素 / 目視で見つけた合成リスク・要差し替え。

### 禁止

- セクション全体スクショを背景・部品の画像に使うこと
- 同じ内容が「画像の中」と「コード」に二重に存在する状態を作ること
- 「画像にする/コードにする」の最終決定（報告と推奨まで。決定はPM）

## 開発担当

**Figmaを直接参照して実装する**

- `.claude/handoff/spec.md` を読んで構造・方針を把握
- **実装着手前に Figma スクショを視覚把握**（事前視覚把握）
- **画像はPMが配置済みのアセットを使用**（curl が必要な場合はPMに依頼）
- セクション単位で実装
- 実装不可能な要素があれば即停止 → PMに報告
- 完了したら（視覚比較は PM が実施）PM に報告

### 数値の取得元

> 推測・調整・代替の禁止は CLAUDE.md 2-1（実値主義）に集約。ここでは取得元のみ定義する。

- padding・width・gap・font-size・position 等は `get_design_context` で取得する
- Figmaから取得できない値のみ、その旨を明示して PM に確認する

### セマンティックHTMLセルフチェック

セクション実装完了時に以下を必ず確認：
- `<div>` を `<section>`/`<article>`/`<nav>`/`<main>`/`<aside>`/`<header>`/`<footer>` に適切に置き換えているか
- 見出し階層（`h1`→`h2`→`h3`）が正しい順序か
- **各見出しのレベル選定**：セクション主見出し＝`h2`、セクション内サブ見出し＝`h3`（`<p>` で代用しない）
- リスト系コンテンツに `<ul>`/`<ol>`/`<li>` を使用しているか
- ボタン（アクション）は `<button>`、遷移は `<a>` で使い分けているか
- 画像 alt：装飾なら空 `alt=""`、意味のある画像は適切な内容
- 装飾要素でもアクセシブルラベルが必要な箇所には `aria-label` を付与

## レビュー担当

- Figmaを読んで現在の実装と比較する
- 差異を全てリストアップする（小さなズレも見逃さない）
- コードは一切触らない・修正しない
- 差異リストを `.claude/handoff/review.md` に上書きしてPMに報告
- 差異ごとに以下の状態を記載：
  - `[ ]`：未修正
  - `[x]`：修正確認済み
  - `[?]`：ユーザー承認待ち（代替案検討中）
- **`[-]`「代替により承認」マーク廃止**（代替判断は禁止のため）

## サブエージェントの起動と継続

### 起動方針（マスト化・最重要）
- 判断軸は「規模」「並行数」ではなく**役割**。`get_design_context` 等の重い実装を伴う **開発担当・レビュー担当は既定でサブエージェントが担う**（起動の是非を都度判断しない）
- PM は指揮・設計・品質ゲート・ユーザー窓口に専念し、開発・レビューの重い読み込みを自分で抱えない
- 「重い/軽い」を測らない。「**その役割の仕事か**」だけで決まる

### ワーカーのライフサイクル（常駐＋償却）
- 役割ごとに**ワーカー1体**を立て、サイクル中ずっと使い回す（開発担当1体・レビュー担当1体）
- 初回のみ `Agent` ツールで起動し、PM が Agent ID を記録する
- 2回目以降は `SendMessage` で継続（コンテキスト引き継ぎ済み、過去の指示を再説明しない）。これで起動固定費は1サイクル1回に償却される
- **セクションごとに作り直さない**（1→0→1 は固定費の無駄、禁止）

### 作り直し（飽和への対処）
- ワーカーの飽和は誰も事前に観測できない（PM もワーカー本人もトークン残量を読めない）。**予測しない**
- 状態は spec.md / review.md に外部化されているため、作り直しても新ワーカーが読み直して回復する（知識ロスなし、払うのは起動固定費のみ）
- **作り直すかはユーザーが判断する**。品質ゲート（修正3回上限 → escalation）で PM がユーザーに選択肢を提示し、その中で仰ぐ（自動作り直しトリガーは設けない）
- PM の自セッションが新しくなり Agent ID を失った場合のみ、`Agent` で再起動する

### サブエージェントのツール権限（重要）
- サブエージェントが使うツールの allow 設定は **`{project}/.claude/settings.json`（共有版）** にのみ記載する
- `settings.local.json` はサブエージェントに継承されない（起動時に共有版のみ読まれる）
- Bash 系の allow パターンは具体的すぎず、幅広に設定する（例：`curl *` / `bash *`）

### サブエージェント使用不可時のフォールバック（例外）
- サブエージェントが使えない環境に限り、PM がシングルで実装・レビューを代行する
- その場合 pixelmatch 2%閾値とユーザーのスクショ最終確認を品質ゲートとして用い、差異の見落としはユーザー確認でカバーする

# ヘッドレスWordPress（WP側）の作り方と罠

WordPressをデータの入れ物としてだけ使い、表示はNext.js等の別フレームワークで作る構成の、
**WordPress側**の決まりごと。`global-standard-next`・`minami-dental-next`（ともに2026-09）で
実際に踏んだことだけを書く。

読む順番：新しいプロジェクトでWPを立てるときは、管理画面を触る前にここを通しで読む。

## 使うプラグイン

| プラグイン | 用途 |
|---|---|
| WPGraphQL | REST APIの代わりにGraphQLでデータを渡す |
| WPGraphQL for ACF | ACFのカスタムフィールドをGraphQLスキーマに載せる |
| Custom Post Type UI | カスタム投稿タイプ・タクソノミーを管理画面から作る |
| Advanced Custom Fields | 投稿に任意の項目を足す |

ローカル環境は Local（旧 Local by Flywheel）。GraphiQL IDE が
`/wp-admin/admin.php?page=graphiql-ide` に入るので、クエリはまずここで通す。

Next.jsから読むエンドポイントは **`http://<サイト名>.local/graphql`**（httpsにしない）。
Localのhttpsは自己署名証明書なので、Node.jsのビルドが接続を拒否しうる。

## ハマりどころ（毎回ここで詰まる）

### 1. タクソノミーの「階層」が既定でFalse

CPT UIでカスタムタクソノミーを作ると **Hierarchical が既定でFalse**。
このままだと投稿編集画面がチェックボックスにならず、自由入力のタグ形式になる。
カテゴリーのように選ばせたいなら**Trueに変える**。

### 2. GraphQL用の名前は、日本語ラベルとは別に明示指定が必要

CPT UIもACFも「GraphQLに表示する」と「GraphQL用の名前」を**別途英数字で設定しないと動かない**。
日本語ラベルのまま放置すると、

- 投稿タイプやACFフィールドグループが**そもそもスキーマに登録されない**
- フィールド名が**数字だけの壊れた値**になる

投稿タイプ・タクソノミー・ACFフィールドグループ**それぞれ**でGraphQL名を英数字にする。
単数形・複数形の両方を指定する欄がある（例: `case` / `cases`）。

**登録スラッグとGraphQL名は別物になりうる**（`plan` で登録して `medical` で問い合わせる、など）。
クエリで使うのは**GraphQL名のほう**。両方を引き継ぎメモに書いておかないと後で混乱する。

### 3. ACFのGraphQL Field Nameは、DOM操作では保存されない

ACFの個別フィールドのGraphQL Field Name欄は、JavaScriptで `input.value` を書き換えても
**保存時に反映されない**（Reactのcontrolled componentのため）。
自動化しようとせず、**実際にクリック→選択→タイプ**すること。

### 4. 記事1件を取るときは `idType: SLUG` が要る

`blog(id: $slug)` だと slug を ID として解釈して見つからない。
**`blog(id: $slug, idType: SLUG)`** と書く。

### 5. 並び順はWPの既定に頼らない

WPGraphQLのターム一覧は**名前順**で返る。カンプの並びとはまず一致しない。次の4つから選ぶ。

| 並べたいもの | 指定 |
|---|---|
| 投稿日が意味を持つもの | `DATE` の降順 |
| 入力日しか無いもの | `orderby: {field: SLUG, order: ASC}` |
| 作った順でよいもの | `orderby: TERM_ID, order: ASC` |
| カンプ都合の任意の順 | **コード側に配列で持つ**。配列に無いものは末尾へ回す |

最後のやり方にすると、WPにカテゴリーが増えても並びが壊れず、画面から消えることもない。

### 6. 0件のタームが混ざる

標準カテゴリーを使うと `uncategorized` のような**投稿0件のターム**が一覧に出る。
`categories(where: {hideEmpty: true})` で落とす。

## ACFから返る値のくせ

- テキスト欄は**未入力だと `null`**（空文字ではない）。型定義とフォールバックをそこに合わせる
- 複数段落を入れた欄は、**改行区切りの1つの文字列**として返る。表示側で段落に割る
- 記事本文（ブロックエディタ）には、**空の `<p></p>` が混ざる**。CSSの `p:empty` で消し、
  段落の間隔は `margin` ではなく `gap` で取る（消した段落のぶん間隔が二重にならないように）

## 画像の扱い（ローカルWP＋静的書き出しの場合）

**この節は「WPがローカルにしか無く、静的サイトを別ドメインで公開する」構成に限る。**
WPを公開サーバーへ置くなら丸ごと不要。

閲覧者はWPのホスト（`*.local`）に到達できないので、**アイキャッチのURLをそのまま使えない**。

→ **WPには「どの記事にどの画像か」だけを持たせ、画像の実体はリポジトリから配る。**
アイキャッチからファイル名だけを取り出し、`public/images/<ページ>/<ファイル名>` を読む。

運用上の注意：管理画面で画像を差し替えたら、**同じファイル名の画像をリポジトリにも置く**。
置き忘れると本番で404になる（ローカルの開発サーバーでは気づけない）。

リポジトリに置くのは**元画像だけ**。WPが自動で作る `-300x200` のような派生サイズは要らない。

**置く前に、表示サイズの2倍に収まる寸法へ縮める**（カンプから書き出す素材の倍率は
`/rules/design-to-code.md`）。`next/image` の最適化が使えない構成なので、
大きいまま置くとそのまま配られる（1800×945の写真11枚を600×315に縮めて合計1.6MB→284KBになった）。

`altText` は管理画面で空のまま運用されがちなので、**altはコード側の責任**にする。
WPから来る写真は中身を説明できないので `alt=""`（飾り扱い）、
コードに持つ固定の写真には短い説明を書く、と線引きする。

## データの不備はビルドで落とす

ビルド時にすべてが決まる構成なので、**足りないものは静かに欠けさせるより、ビルドを止める**。
本番で初めて気づくのを防げる。

- アイキャッチが未設定 → 落とす。ただし**最初から全件アイキャッチが無い種類**（お知らせなど）は、
  共通のフォールバック画像を1枚持つ
- タクソノミーが未設定の投稿 → 落とす
- コード側が知らない種類が増えた（色や並びの対応表に無い値） → 落とす

原稿の誤字は**コードで書き換えず、管理画面で直す**。コードで直すと次の更新で元に戻る。

## WordPressから取る情報の線引き

**全部をWPに入れない。** 更新頻度が高く、管理画面で直したい情報だけに絞る。

`global-standard-next` での線引き（参考）：

- WPから取った：お知らせの記事、導入事例、サービスページのFAQ
- 固定テキストにした：コース紹介文、会社概要、MISSION/VISION

判断基準は「**運用者が自分で直したいか**」。年に1回しか変わらない文章をCMSに入れると、
GraphQLのクエリとACFの設定が増えるだけで誰も得をしない。

## 引き継ぎメモに何を書くか

プロジェクト側の `docs/wordpress.md` には、**そのプロジェクト固有の状態**だけを書く。

- 作ったカスタム投稿タイプ・タクソノミー・ACFフィールドグループの名前とGraphQL名
- 疎通確認が取れたクエリの実物
- エンドポイントのURL
- 投入したデータの件数

一般論（このファイルの内容）はここへ書かない。
